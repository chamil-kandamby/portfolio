Engineering practice

  1. Scope agreed in writing

    Before any code, we agree what the app must do, what is out of scope, and how each milestone will be accepted. Changes are discussed and agreed, never assumed.

  2. Short milestones, regular demos

    Work is split into small milestones, each with a build you can try. It is the same Agile rhythm I have run with distributed teams for years.

  3. Code another developer can maintain

    Clear structure and naming, linting and consistent formatting, and a Git history of small, described changes. Nobody should need me to understand it.

  4. Automated tests, end to end

    Unit and integration tests on business rules, permissions and anything involving money, plus Playwright end-to-end tests that drive the real app in Chromium, Firefox and WebKit, phone screens included. They all run on every change.

  5. Performance tested with k6

    Load, stress and soak tests written in k6 against realistic user journeys, with pass or fail thresholds on response time and error rate. You learn how much traffic the app can take before launch day, not on it.

  6. Automated build, release and monitoring

    A CI/CD pipeline builds, tests and deploys each version. Separate test and live environments, versioned releases with a way back, and logging with error alerts so problems surface before your users report them.

  7. Documentation and a clean handover

    A README, setup and deployment steps, and API documentation, with the full source in your own repository. You own everything, and nothing depends on me.

Security by default

  1. No secrets in code

    API keys, passwords and connection strings live in environment settings or a key vault, never in the repository or inside the app. Each environment has its own, and each service account gets only the access it needs.

  2. Sign-in and permissions done properly

    Proven identity providers and standards such as OAuth 2.0 and OpenID Connect. Passwords are stored only as strong one-way hashes, and permissions are checked on the server for every request, not just hidden in the interface.

  3. Every input treated as untrusted

    Server-side validation, parameterised database queries and encoded output, with the OWASP Top 10 as the checklist: injection, broken access control, cross-site scripting and the rest. Public endpoints are rate-limited.

  4. Personal data kept to a minimum

    HTTPS everywhere and data encrypted at rest. The app collects only what it needs, and no personal data or tokens are written to logs. Card payments go through a payment provider, so card numbers never reach your servers.

  5. Mobile and device security

    Sign-in tokens kept in the phone's secure storage (Keychain on iOS, Keystore on Android), release builds signed and obfuscated, and Bluetooth links between app and device paired and encrypted.

  6. Dependencies kept current

    Packages from official sources with pinned versions, automated vulnerability alerts, and security updates applied promptly. At handover, accounts and keys move to you and my access is removed.

An honest limit: I build securely, but I am not a penetration tester. For apps that handle payments, health records or other sensitive personal data, I recommend an independent security test before launch, and I will work with whoever runs it.
